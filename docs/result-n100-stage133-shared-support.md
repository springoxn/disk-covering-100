# 阶段133：共享支持上下文与哈希失效

[共享支持会话](../verify/n100_shared_support_session.py)不接收调用方提供的ctx。构造时重放65536透镜条带及513自由截距支持约束；两条规则使用同一个已核验透镜。受限截距支持和自由截距支持只逻辑求交，面积亏损不相加。

[实验入口](../verify/run_n100_shared_support_timing.py)实际执行：

```powershell
python verify/run_n100_shared_support_timing.py --run-dir runtime/shared-support-133
```

退出0。[证据](../verify/out/n100-shared-support-session.json)记录7个不同进程的成对冷准备，block内随机决定分别重建/共享的次序，并记录5次热调用。m=100、k=32/42/54/55四个输入的判定和精确面积缺额均与原公共适配器逐项一致；前三个保留、k55排除。这不是当前404标签域的新增排除。

## 实测

|方式|7轮中位数|
|---|---:|
|两位消费者分别重建完整支持会话|3499.4957ms|
|两个消费者共享一次会话|1718.0684ms|
|共享会话四个输入热调用，逐次检查当前文件哈希|34.7572ms|

冷准备比约2.03688。重复模式确实重建两套会话、各核验一次条带和支持；共享模式构造一套。它比较两个相同消费者在相同证明前提下是否重复准备，不是拿完整径向轮廓准备与只核验透镜进行不公平比较。

会话在本实验绑定29个本地已加载源和数据文件；每次公开run均重读内容核对SHA256。热调用包含内容哈希和证书绑定复制成本，因此显著慢于先前只调用内部ctx公式的约0.02ms。内存命中、哈希核验和精确公式成本必须分开记，不能直接把内部公式时间作为安全公开调用成本。

## 四个控制

1. 半径改为U-10^-12：拒绝，不隐式把固定服务数转移到其他半径。
2. 内存中预期证书/源哈希被篡改：拒绝；不修改任何实际源文件。
3. 内容快照不同：snapshot_valid为false，缓存键不得命中。
4. 调用方修改返回结果中的binding：后续会话绑定不受影响。

七轮均通过。第2项在同一核验函数中模拟预期值与当前内容不相等；第3项直接验证快照判等。并未为了测试去改写数学证书或源码。

## 证明范围

支持有效性依赖原来的norm-cap规范化、短弧公式、面积次可加性等解析前提。会话重新核验条带、源与证书链，不宣称重新证明这些解析引理。自由截距最优性仅针对保存矩形包络的k54目标。

本地导入源模块被加入内容绑定，但标准库/第三方包仍属于记录的Python环境。当前已加载模块的源码与运行中字节码对应性沿用环境信任，不是形式内核核验。调用前哈希检查以本地稳定快照为前提，不提供抵抗并发恶意写入的原子文件系统保证。

若证据或源改变，旧会话拒绝后须重建；新会话若旧证书不再绑定新源，应拒绝而不能自动更新历史hash。外部任意ctx和任意字典不能作为SupportSession对象输入，原内部apply方法仍只给经认证构造路径调用。
